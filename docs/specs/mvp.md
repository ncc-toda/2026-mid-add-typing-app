# トラブルベース打 — MVP 仕様書

ITエンジニアのチャット返信を模したタイピングゲームの MVP 仕様。  
ゲームルールと UI 方針を正とする。実装で確定した識別・保存・ローマ字・係数は **12. 実装で確定したルール** を参照する。

---

## 1. ゲームの一文

今どきのトラブル多め IT 企業で、Slack 風チャットに届く依頼へ、カタカナ語好きの主人公として返信を打ち、制限時間内の「年収」を稼ぐタイピングゲーム。

---

## 2. 世界観

### 2.1 舞台

- 会社名: **株式会社トラブルベース**（TROUBLEBASE Inc.）
- 事業: Web アプリ開発が主力。障害・炎上が日常の、今どきの IT 企業
- 部署: Webアプリ開発部（フルスタック）
- コミュニケーション: Slack 風ワークスペース上のチャンネル / DM

### 2.2 主人公

- 新配属のフルスタックエンジニア
- カタカナ語を使うほどカッコいいと思っている
- **1返信に必ず 1 つ、冗談またはボケを入れる**（入れないと気がすまない）
- 表示名（仮）: `オオダ`
- ステータス: オンライン

難易度によって口調とボケの強さが変わる（3.2 参照）。

### 2.3 相手役

上司・同僚・カスタマーサクセス・たまに顧客。Slack 上の表示名とアイコンで区別する。

例:

- `サトウ` — 開発マネージャー（依頼・進捗確認が多い）
- `タナカ` — 同じチームのエンジニア（バグ報告・メンション）
- `CS-ヤマダ` — カスタマーサクセス（顧客経由の問い合わせ）
- `クライアントA` — 顧客（丁寧めの連絡。登場は中級以上を想定）

### 2.4 チャンネル例

- `#web-app` — 日常の開発連絡
- `#incident` — 障害・炎上
- `#customer-success` — 顧客対応の橋渡し
- `#random` — 雑談混じりの依頼

## 3. 難易度

3 段階。制限時間は共通で 60 秒。差は文章の長さ・記号量・口調で出す。

### 3.1 初級（新米エンジニア）

- 短い返信、簡単なやり取り、記号は少なめ
- 社会人としての初々しさ。丁寧語が基本
- ボケは控えめ（「一旦リサーチします…（5分）」程度）
- カタカナ語は 1 返信に 1 語前後

### 3.2 中級（慣れてきたエンジニア）

- 少し長めの返信
- `@` メンション、Issue / PR 番号、軽い Markdown、英数字・記号を含む
- ちょっと調子に乗り始める
- カタカナ語が増え、自分の仕事を盛って言いがち

### 3.3 上級（つよつよエンジニア）

- 長め・複数行の返信
- Markdown、引用、技術用語、英数字・記号を多く含む
- 自分に絶対的な自信がある。ボケも大きい
- カタカナ語を畳みかける

### 3.4 題材

実業務で使いそうなコミュニケーションに限定する。

- 確認・レビュー依頼
- バグ報告
- 進捗報告
- 質問
- 顧客への連絡
- `@` メンション
- 多少 Markdown のような記法を取り入れた構造的な文章
- Issue / PR 番号
- 英数字や記号を含む文章

**含めないもの:** URL 全文など、タイピングゲームとして入力負荷が極端に高いもの。ドメイン名やパスの断片が必要な場合は短いトークンにとどめる。

## 4. 1 プレイの流れ

```text
タイトル
  ├─ 難易度選択 → カウントダウン → プレイ（60秒） → 結果
  └─ 統計
結果からタイトル / 統計へ戻れる。
```

### 4.1 制限時間

- MVP では **60 秒固定**
- 難易度は文章側で変える。30 秒 / 90 秒は対象外

### 4.2 プレイ中の進行

1. 短いカウントダウンのあと、最初の相手メッセージが表示される
2. 自分が打つ返信文が入力欄（および進捗表示）に提示される
3. プレイヤーはローマ字でかなを追う
4. **全文一致した時点で自動送信**（送信キーは不要）
5. 年収が加算される（昇給演出）
6. 次の相手メッセージが届く
7. タイムアップまで 2〜6 を繰り返す

### 4.3 タイムアップ

- 入力は打ち切る
- **未送信の途中返信は年収に含めない**
- 結果画面へ遷移する

### 4.4 シナリオの出題順

- 同じ難易度内のシナリオ（メッセージ＋返信の組）をランダム順で出す
- 可能なら、直前のプレイと先頭が重複しにくいようにする
- プールを使い切ったら再シャッフルしてよい

### 4.5 年収のリセット

- タイトルに戻ると、そのプレイの年収表示はリセットされる
- **ハイスコア（難易度ごとの最高年収）は保存する**（MVP 対象）
- 統計用のキー単位ログはプレイをまたいで残す

## 5. 入力ルール

ゲームルールとしての入力。実装技術は規定しない。

### 5.1 基本

- 画面上の返信は日本語（漢字かな混じり）
- プレイヤーはローマ字入力で、現在位置のかな / 記号まで追う
- 入力欄に IME 変換は使わない想定（ゲームとしてローマ字を直接受け取る）

### 5.2 ミス

- **誤りキーはミスとして数え、対象のかなは進まない**（強制正確）
- ミス時は視覚的なフィードバック（対象文字の強調、短い揺れなど）を出す

### 5.3 ローマ字のゆらぎ

一般的なローマ字のゆらぎは正解とする。例:

- `si` / `shi`
- `ti` / `chi`
- `tu` / `tsu`
- `hu` / `fu`
- 撥音の `n` / `nn`（後続に応じた通例どおり）
- 長音（ー）および母音の伸ばし

詳細な対応表は本実装時にゲームルールとして確定してよい。MVP では「一般的な日本語ローマ字のゆらぎを受け入れる」を原則とする。

### 5.4 英数字・記号・改行

- 英数字、記号、改行、Markdown 記号（`` ` `` `*` `-` `>` など）は **表示どおりのキー**
- 全角記号を出題に含める場合は、打つべきキーを画面上で誤解なく示す

### 5.5 コンボ

- 連続した正解キー数がコンボ
- ミスでコンボは 0 に戻る
- そのプレイ中の最大コンボを結果画面に出す

## 6. スコア

### 6.1 メインスコア

**ゲーム内年収（万円）**

- プレイ中も結果画面も同じ単位
- 1 返信を送り終えるたびに「昇給」として加算する

### 6.2 1 返信の獲得額

```text
獲得額（万円）= round(基礎額 × 速度係数 × 正確性係数)
```

#### 基礎額

難易度と「重み付き文字数」で決める。

- 重み付き文字数: 通常文字は 1、英数字・記号・改行は 1.5
- 初級: `15 + 重み付き文字数 × 0.5`
- 中級: `28 + 重み付き文字数 × 0.7`
- 上級: `45 + 重み付き文字数 × 0.9`

#### 速度係数

- その返信の KPM = `正解キー数 ÷ その返信にかかった秒 × 60`
- 難易度基準 KPM: 初級 220 / 中級 300 / 上級 380
- `速度係数 = clamp(実KPM / 基準KPM, 0.6, 1.4)`

#### 正確性係数

- 正確性 = `正解キー / (正解キー + ミス)`（キーが 0 のときは 0）
- `正確性係数 = 0.7 + 正確性 × 0.45`（正確性 0% で 0.7、100% で 1.15）

端数は四捨五入し、万円単位の整数にする。

### 6.3 目標レンジ

60 秒プレイで、上手いプレイがおおよそ **400〜1500 万** に見えることを狙う。

- 初級: 短文を多め（件数で稼ぐ）
- 上級: 長文で件数は少なめ（単価で稼ぐ）

極端に外れる場合は、基礎額や係数を調整する。

### 6.4 結果画面のサブ情報（そのプレイのみ）

- 入力速度（プレイ全体の KPM）
- 正確性（%）
- ミス数
- 最大連続入力数（最大コンボ）
- 送信した返信件数（あると結果が読みやすいため表示してよい）

### 6.5 ハイスコア

- 難易度ごとに最高年収を保存する
- タイトルまたは結果で参照できるようにする

## 7. タイピング分析

各プレイのキー単位ログを蓄積し、専用の統計画面で合計表示する。  
高度な時系列・推移グラフは MVP 対象外。

### 7.1 苦手キー

物理キーごとに:

- 入力回数
- ミス回数
- ミス率

ミス率が高い順に並べる。

### 7.2 苦手な指

JIS 配列のホームポジション対応で集計する。

- 左小指 / 左薬指 / 左中指 / 左人差指
- 右人差指 / 右中指 / 右薬指 / 右小指
- 親指（スペース）

キーと指の対応は一般的な日本語キーボードの指使いとする。

### 7.3 苦手な動き

連続する 2 キー（物理キーの遷移）ごとにミス率を集計する。  
例: `k` → `y`（「き」を打つ動き）

### 7.4 空状態

プレイ数が少ない、または該当キーの入力回数が閾値未満のときは **「データ不足」** と出す。  
閾値の目安: そのキー（または遷移）の入力が 5 回未満。

### 7.5 リセット

統計のリセットはあってよい。実行前に確認ダイアログを出す。

## 8. 画面一覧（MVP）

| 画面 | 役割 | 備考 |
| --- | --- | --- |
| タイトル | 世界観、スタート、統計・ハイスコアへの入口 | |
| 難易度選択 | 初級 / 中級 / 上級 | 性格差が伝わるコピー |
| プレイ | Slack 風チャットで返信を打つ | 年収・残り時間・コンボ |
| 結果 | 年収とサブ指標 | タイトル / 統計 / もう一度 |

### 8.1 MVP 対象外の画面

設定、アカウント、ランキング、長いチュートリアル。

初回のみ、入力欄付近に短い操作説明を出してよい。

### 8.2 UI/UX 方針（選定済み）

共通の前提:

- Slack でやり取りしている風のチャット画面
- 今どきの IT 企業っぽいテイスト
- 白をベースとしつつ、ビビッドな色を多数使い、カラフルでポップ

**本線は Pattern B: Arcade HUD**（モック比較で選定）。

比較した案:

- A Workspace: 左チャンネル・右レール。業務画面の密度が高い
- **B Arcade HUD: 採用。** 年収と残り時間が大きく、入力欄がステージ
- C Colorful DM: サイドバーなしの単列。余白と吹き出し重視

他パターンからの取り込みは、選定時点では行わない。A のチャンネル一覧や C の単列レイアウトは本線にしない。

#### ビジュアル

- 白〜クリーム基調の上に、黄・オレンジ・シアン・ライムなど高彩度の面
- 黒の太い枠、ずらしたドロップシャドウ（ゲーム盤面らしい輪郭）
- 丸ゴシック系の太めの字体
- チャットは中央のカード。吹き出しは相手グレー、自分は黄色系

#### 画面ごとの方針

- **タイトル:** スタンプ風の「60秒チャレンジ」、大きなタイトル、スタートと統計。難易度別ハイスコアを並べる
- **難易度:** 3 枚の色面カード（緑／オレンジ／ピンク）。時間は共通 60 秒である旨を短く書く
- **プレイ:**
  - 最上段 HUD: 左にロールとコンボ、中央に巨大な年収、右に残り時間
  - 中央: チャンネル名チップ（例 `#incident`）＋ Slack 風メッセージ列
  - 送信済み返信の近くに「昇給 +○万」
  - 最下部: 暗い「ステージ」上に、打つ日本語（済／現在／残り）とローマ字ヒント
- **結果:** TIME UP スタンプ、年収をいちばん大きく、その下に速度・正確性・ミス・最大コンボ
- **統計:** 同じ枠線・色面のトーンで、苦手指・キー・2キー遷移を表で出す

モックの参照: [`mockups/pattern-b/`](../../mockups/pattern-b/)（比較ハブは [`mockups/index.html`](../../mockups/index.html)）

## 9. コンテンツ量（MVP）

- 難易度ごとに、メッセージ＋返信の組を **12 件以上**
- 本仕様にはサンプルのみ載せる。全文リストは本実装時に揃える

### 9.1 初級サンプル

**1. レビュー依頼**

- 相手 (`サトウ` / `#web-app`):  
  `PR #12 のレビューお願いできますか？`
- 返信:  
  `確認します。少々お待ちください。`

**2. バグ報告**

- 相手 (`タナカ` / `#web-app`):  
  `ログインボタン押しても反応ないです`
- 返信:  
  `再現します。一旦リサーチします…（5分）`

**3. 進捗**

- 相手 (`サトウ` / `#web-app`):  
  `今日の進捗どう？`
- 返信:  
  `チケット2件クローズしました。快調です！`

**4. 質問**

- 相手 (`タナカ` / `#web-app`):  
  `ステージングのURLってどこでしたっけ`
- 返信:  
  `後で共有します。ブックマーク迷子です…`

### 9.2 中級サンプル

**1. レビュー＋メンション**

- 相手 (`サトウ` / `#web-app`):  
  `@オオダ PR #123 レビューまだ？今日中希望です`
- 返信:  
  `@サトウ 確認中です。LGTM狙いで見ます。コーヒーブレイク後には返します。`

**2. バグ＋Issue**

- 相手 (`タナカ` / `#incident`):  
  `本番で 500 出てます。Issue #88 切りました`
- 返信:  
  `オンコール的に見ます。再現手順ください。僕のせいだったら餅つきします。`

**3. 軽い Markdown**

- 相手 (`CS-ヤマダ` / `#customer-success`):  
  `顧客から「保存できない」と。優先度高でお願いします`
- 返信:  
  `了解です。\n- 対象: 保存API\n- 暫定: リトライ\nデバッグしながら盛って直します。`

**4. 進捗**

- 相手 (`サトウ` / `#web-app`):  
  `リリース作業の見積もり教えて`
- 返信:  
  `2時間バッファ込みです。フラグは `enable_new_form` 。余裕のフルスタックです。`

### 9.3 上級サンプル

**1. 複数行＋引用＋自信**

- 相手 (`サトウ` / `#incident`):  
  `決済が落ちてます。顧客から怒りのメンション来てます`
- 返信:

```text
> 決済が落ちてます

原因は timeout と判断。PR #402 で retry 入れます。
- 暫定: キュー再投入
- 恒久: タイムアウト延長

僕が出るとインシデントが静かにします。たぶん。
```

**2. Markdown＋技術用語**

- 相手 (`タナカ` / `#web-app`):  
  `@オオダ N+1 疑いで遅延してる。誰か見て`
- 返信:

```text
@タナカ 既にプロファイリング済みです。
`User.includes(:orders)` で解消予定。
ベンチは 1.8s → 120ms。神です。僕が。
```

**3. 顧客連絡（社内下書き）**

- 相手 (`CS-ヤマダ` / `#customer-success`):  
  `顧客向けの謝罪文ドラフトお願いします。今日中`
- 返信:

```text
件名: 障害のお詫び
本文:
ご迷惑をおかけし申し訳ございません。
現在は復旧済みです。再発防止をコミットします。
（社内向け: 盛ってないです。今回は本当です）
```

## 12. 実装で確定したルール

授業指定の技術スタック（React / TypeScript / Vite+ / Hono / Cloudflare Workers / D1）は本節の対象外。ゲームとして実装時に決めたことだけを書く。

### 12.1 匿名プレイヤー

- 初回アクセス時に UUID を生成し、ブラウザの `localStorage`（キー `tb_player_id`）に保存する
- API には `X-Player-Id` ヘッダで渡す
- 氏名・メール・IP などの個人情報は保存しない
- 本格的なログインはつけない

### 12.2 キー入力と保存

- プレイ中のキーイベントはバックエンドへ送らない
- ブラウザ内で記録・集計し、タイムアップ後に結果をまとめて 1 回保存する
- 保存するのはプレイサマリ（年収、KPM、正確性、ミス、最大コンボ、送信件数）と、キー／遷移の集計

### 12.3 返信の読み

- `reply_text` は画面に出す漢字かな混じりの返信
- `reply_reading` は入力判定用。日本語はひらがな、英数字・記号・改行は表示どおり
- `reply_units` は `{ display, reading }[]`。表示の進捗ハイライトと読みを対応させる

### 12.4 ローマ字

一般的なヘボン式のゆらぎを受理する。対応表とオートマトンはゲームロジック側で固定する（[`docs/decisions/0001-romaji-engine.md`](../decisions/0001-romaji-engine.md)）。

### 12.5 統計リセット

統計画面のリセットはキー／遷移の累計だけ消す。難易度ごとのハイスコア（plays の最高年収）は残す。
